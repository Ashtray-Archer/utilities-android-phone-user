# Recipe-first implementation: incomplete

`RecipeShopping.idric` implements pure recipe and shopping decisions under
`examples/autogenerated/green-grocer-recipes/`. It extends the existing cart
specimen's semantic path with dynamic recipe/product identities and collections.
It does not replace `model/cart.c`, `android/main.c`, the package identity,
signer or producer policy. The original C implementation still owns the old
Android sample application until the Idriç runtime can be integrated.

## Implemented and executed on the host

- Exact rational quantities; mass, volume and count remain distinct.
- Positive serving counts; shared ingredient aggregation before package rounding.
- Pantry subtraction, with zero-demand rows retained as pantry-covered.
- Separate ingredient, internal product, retailer/store product and checkout IDs.
- Explicit approval and permitted-substitution intersection across recipes.
- Whole-package counts, purchased amount, surplus and exact USD cents.
- Missing, ambiguous, out-of-stock, unknown, changed and unpriced products.
- Recipe save/edit/select, servings, pantry, store, observation, match approval,
  navigation/back and final cart-review transitions. Recipes is the initial state.
- Item-level handoff result values, including unknown outcomes after lost replies.

`check-recipes.grease` builds and executes 37 independently expected host cases
and three implementation mutations. The mutations ignore pantry stock, round
packages down and accept changed prices; each compiles and is rejected by the
intended behavioral assertion. The test also runs the same runtime probe on
the host. It does not substitute typechecking for execution.

The historical 2264-cent C fixture expectation is included, but the C executable
was **not rerun** in this environment: no qualified pinned ICK/NDK installation
was present. Full C-oracle comparison remains required. `fits_c_oracle` checks a
conservative bounded projection; its bounds do not limit recipe-domain values.
`cart_total` sums resolved lines only; an incomplete plan must display that
number as a partial subtotal and keep unresolved ingredients visible.

Invoke maintained Grease helpers with explicit absolute repository, frontend,
driver and fresh evidence paths; each prints its argument interface without
arguments. Frontend is pinned to
`740bbf2b1d9e811fd00c719c3473eede17ceea3b`. Host Chez is a semantic control, never
the Android application backend. Some local Grease builds include LeakSanitizer;
this container needed `ASAN_OPTIONS=detect_leaks=0` because LeakSanitizer cannot
enumerate the traced process. That setting changes no application test.

## Actual compiler boundary

`RecipeRuntime.idric` wraps the actual domain operations in legal Int32/Text
observation exports. Its source checks and runs on the host. The canonical
android-NDK DEX driver rejects package arithmetic with:

```text
Recursive checked helper is not in the DEX specialization slice: Data.Nat.div'
```

Compiler exit is 1; no candidate `recipes.dex` exists. This is not a failure of
the source ABI and does not establish that all records or all lists are
unsupported. `SavedRecipeRuntime.idric` isolates the real save transition and
emits independently disassembled DEX. That is emission evidence only; ART and
physical-device execution remain NOT_RUN.

Backend source started at `isomorphisms/android-NDK`
`de29100e9b24b5bbc85aca7f77cd3b08c0934917`. Two reserved `prefix` bindings in
`Placement.idr` prevented a fresh build; renaming them restored it. The existing
runtime-argument test also needed a layout-only repair to parse. Its host
encoder/refusal checks then passed; that result does not establish ART behavior.

The reduced checked program, emission gate and independent ART observer live in
the canonical backend's `examples/autogenerated/green-grocer-package-rounding/`.
The next compiler change must preserve exact Number semantics while lowering
its recursive numeric helper. Narrowing to Int32, replacing rounding in C, or
recognizing this particular source program would evade the requirement.

No ADB, emulator or ART runtime was available in this execution environment.
No authorized Kroger application/customer session was supplied or exercised.
Retain the existing package `org.isomorphisms.greengrocer` and signer recorded
in `README.md` when packaging becomes possible. Never pass the old product
sample APKs off as this recipe-first application.

The [recovered Kroger research](kroger-api.md) includes the current public
collection's PUT `/cart/add` correction. OAuth, mobile redirect/PKCE details,
request body/modality, revalidation timing, retry/reconciliation and item-result
granularity still require verification before a live adapter is implemented.
The adapter must fetch a fresh observation before an approved handoff and
invalidate review whenever that observation or any shopping decision changes.
It must persist submitted/unknown item outcomes before permitting another add;
`prepare_handoff` is a pure proposal, not a network write or retry mechanism.
Payment and order completion remain with the retailer.
