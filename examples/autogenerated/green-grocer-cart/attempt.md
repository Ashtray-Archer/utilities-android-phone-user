## Type sketch

The fixture catalog has exactly three semantic product identities: bananas,
apple bags and cereal. Identity membership is represented by a closed choice,
not by a display name or a list position. A positive amount stores the Number
of additional units beyond one; its observation is `S additional_units`.
Absence is a separate choice. Consequently no coordinate can store zero.

A cart is a product-indexed function returning absent or a positive amount.
This is an inspectable representation of a finite sparse map: absence means
no map entry. It is not a new general-purpose map library.

Central operations are pure:

- `set_amount : product_identity → Number → cart → cart` normalizes zero to
  absence and a successor to a positive amount.
- `add : product_identity → cart → cart` increments one coordinate.
- `remove : product_identity → cart → cart` clears one coordinate.
- `total_cents : cart → Number` derives the exact weighted sum.
- `rename_cart : (product_identity → product_identity) → cart → cart` accepts
  the inverse identity mapping. The concrete swap below is its own inverse.

The semantic operations have no effects. `main` prints the derived sample
total as a minimal observable demonstration. Propositional equality declarations request
compiler checking of fixture arithmetic, zero removal, removal from empty,
positivity of a constructed amount, and the coordinate-renaming law for add.
These declarations are obligations until the actual compiler checks them.

Number is unrestricted nonnegative whole-number vocabulary in the current
canonical compiler documentation. The historical cart note's claim that
Number itself is positive must not be relied upon. This attempt explicitly
encodes positivity. Machine-width bounds in the C program are a distinct
representation boundary; this experiment uses unbounded Number.

Required primitives: current filename-scoped `choice`, `Number`, successor
pattern matching, pure functions, multiplication/addition, propositional
equality and `Refl`, plus output at the demonstration boundary. No collections,
FFI, persistence or Android is required.
The desired handoff is the canonical compiler's `--emit-one-step`, followed by
inspection against a maintained backend's explicitly supported surface.
